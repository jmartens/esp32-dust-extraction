# ADR-0014:     

**Status:** Accepted

## Context

Early versions of the OpenExtraction architecture assumed a one-to-one relationship between a physical device and its functional role within the system. A Machine Node represented a single machine, a Gate Node represented a single dust gate, and each physical ESP32 hosted exactly one logical function.

As the architecture evolved, it became desirable to support more capable hardware configurations. A single physical device may monitor multiple machines, control multiple gates, or combine different functions such as machine monitoring, gate control, environmental sensing and user interaction.

Maintaining a one-to-one relationship between physical devices and logical functions would unnecessarily constrain hardware design and increase system cost.

The architecture therefore requires a distinction between the physical hardware participating in the network and the logical functions managed by the Controller.

---

## Decision

The architecture distinguishes between **Physical Devices**, **Units** and **Capabilities**.

A **Physical Device** represents a single network participant.

A Physical Device SHALL:

- possess a unique Device UID;
- communicate using a single transport endpoint;
- participate in pairing and authentication;
- execute a single firmware image;
- host one or more Units.

A **Unit** represents a single logical function hosted by a Physical Device.

A Unit SHALL:

- belong to exactly one Physical Device;
- possess a Unit Identifier that is unique within the hosting Physical Device;
- have exactly one Unit Type;
- expose zero or more Capabilities;
- be independently addressable by the Controller.

A **Capability** represents behaviour or functionality supported by a Unit.

Capabilities describe what a Unit can do or report.

Examples include:

- Demand Detection
- Current Measurement
- Manual Override
- Open
- Close
- Position Feedback
- Temperature Measurement

Capabilities SHALL NOT define the identity or role of a Unit.

---

## Unit Types

A Unit Type identifies the purpose of a Unit.

Examples include:

- Machine
- Gate
- Collector
- Environmental Sensor
- Relay Output
- Analog Input

Future Unit Types MAY be introduced without changing the overall architecture.

---

## Controller Responsibilities

The Controller SHALL remain the single source of truth.

The Controller SHALL:

- discover Physical Devices;
- enumerate Units hosted by each Physical Device;
- determine supported Capabilities;
- maintain routing based upon Units;
- maintain configuration for Units;
- issue Commands to Units;
- consume Events generated by Units.

Business logic SHALL operate upon Units rather than Physical Devices.

Physical Devices remain implementation details of the transport layer except where device-level operations are required.

Examples of device-level operations include:

- firmware update;
- reboot;
- pairing;
- diagnostics.

---

## Discovery

Discovery SHALL occur at the Physical Device level.

Each Physical Device SHALL advertise the Units that it hosts.

Each advertised Unit SHALL include:

- Unit Identifier;
- Unit Type;
- supported Capabilities.

The Controller SHALL create the corresponding logical representation for every discovered Unit.

---

## Resource Namespace

The hierarchical resource namespace defined by ADR-0012 SHALL distinguish Physical Devices from Units.

Illustrative examples include:

```
/devices/{deviceUid}

/devices/{deviceUid}/units

/devices/{deviceUid}/units/{unitId}

/devices/{deviceUid}/units/{unitId}/config

/devices/{deviceUid}/units/{unitId}/status

/devices/{deviceUid}/units/{unitId}/statistics

/devices/{deviceUid}/units/{unitId}/actions
```

The logical namespace SHALL remain independent of the transport-specific wire encoding.

---

## Rationale

Separating Physical Devices from Units provides several advantages.

A single hardware platform may host multiple logical functions without architectural changes.

Business logic becomes independent of hardware topology.

Routing, configuration and automation operate consistently regardless of how functions are distributed across hardware.

The architecture remains scalable while preserving the Controller as the single source of truth.

---

## Consequences

### Advantages

- Supports multiple logical functions on one Physical Device.
- Reduces hardware cost.
- Improves deployment flexibility.
- Simplifies future expansion.
- Keeps business logic independent of hardware layout.
- Maintains a clear separation between transport concerns and domain logic.
- Preserves backward compatibility with single-function devices.

### Disadvantages

- Discovery becomes slightly more complex.
- Messages identifying Units must include both the Device UID and Unit Identifier.
- Firmware implementations must multiplex requests between hosted Units.

These disadvantages are considered acceptable because they significantly improve the flexibility and longevity of the architecture while avoiding unnecessary coupling between hardware and domain concepts.

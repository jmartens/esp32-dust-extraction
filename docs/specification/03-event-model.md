# Event Model

## Purpose

The OpenExtraction Controller is an event-driven system.

All changes to Controller state SHALL occur in response to one or more Domain Events.

The purpose of the event model is to decouple business logic from hardware, communication transports and user interfaces.

The event model enables independent evolution of Controller Services while preserving deterministic behaviour.

---

# Principles

The event model is based upon the following principles.

- Events represent facts.
- Commands represent requests.
- Events are immutable.
- Commands SHALL NOT directly modify Controller state.
- Controller state SHALL only change while processing Domain Events.
- Business logic SHALL remain independent of transports and hardware.
- Event processing SHALL be deterministic.

---

# Event Lifecycle

External inputs SHALL first be translated into Domain Events before entering the Controller.

Controller Services consume Domain Events.

Controller Services MAY emit:

- Domain Events
- Commands

Commands are dispatched to Physical Devices.

Physical Devices execute Commands and report the resulting Domain Events.

The Controller updates its state only after processing those Domain Events.

---

# Domain Events

A Domain Event represents a business-significant fact.

A Domain Event SHALL describe something that has already occurred.

Domain Events SHALL be immutable.

Domain Events SHALL NOT request behaviour.

Examples include:

- MachineDemandStarted
- MachineDemandStopped
- GateOpened
- GateClosed
- GateFault
- CollectorStarted
- CollectorStopped
- RouteActivated
- RouteDeactivated
- AllRequiredGatesOpen
- RequiredGateUnavailable

---

# Infrastructure State

Infrastructure concerns SHALL remain internal to the owning Controller Service.

Infrastructure state SHALL NOT be published as Domain Events.

Examples include:

- heartbeat received
- heartbeat timeout
- replay detection
- packet validation
- sequence number tracking
- transport retries
- device online status

Infrastructure state MAY be queried by other Services when required.

Infrastructure state MAY be exposed through diagnostics.

---

# Commands

A Command represents a request for another component to perform an action.

Commands are generated by Controller Services.

Commands SHALL NOT directly modify Controller state.

Completion of a Command SHALL be confirmed by one or more subsequent Domain Events.

Examples include:

- OpenGate
- CloseGate
- StartCollector
- StopCollector
- RebootDevice
- PerformCalibration

---

# Event Processing

Events SHALL be processed sequentially.

Processing of one Domain Event SHALL complete before processing begins for the next.

The Controller SHALL preserve event ordering.

Events generated while processing another Event SHALL be appended to the Event Queue.

Recursive event processing SHALL NOT occur.

---

# Event Queue

The Controller SHALL maintain a single Event Queue.

Domain Events SHALL be removed from the queue only after successful processing.

The implementation MAY prioritise categories of Events.

Prioritisation SHALL preserve deterministic behaviour.

---

# Controller Services

Controller Services consume Domain Events.

A single Domain Event MAY be consumed by multiple Services.

Examples include:

- Device Registry
- Routing Service
- Gate Service
- Collector Service
- Configuration Service
- Diagnostics Service

Services SHALL communicate through:

- Domain Events
- Commands
- synchronous queries

Services SHALL NOT directly modify another Service's internal state.

---

# State Changes

Controller state SHALL change only while processing Domain Events.

Commands SHALL NOT directly modify Controller state.

Transport messages SHALL NOT directly modify Controller state.

GPIO interrupts SHALL NOT directly modify Controller state.

Web requests SHALL NOT directly modify Controller state.

---

# Physical Devices

Physical Devices execute Commands.

Physical Devices report Domain Events.

Physical Devices SHALL NOT perform routing decisions.

Physical Devices SHALL NOT perform automation.

Physical Devices SHALL remain unaware of system topology.

---

# Units

Units represent logical functions hosted by Physical Devices.

Business logic operates upon Units.

The hosting Physical Device SHALL remain transparent to Controller Services except where device-level operations are required.

---

# Event Lifetime

Domain Events exist only while being processed.

Persistent storage of processed Events is not required.

Event logging is implementation dependent.

---

# Error Handling

Failure to process one Event SHALL NOT prevent subsequent Events from being processed.

Malformed Events SHALL NOT modify Controller state.

Unexpected Events SHALL be ignored or logged.

# Summary

The OpenExtraction event model ensures that:

- Events represent facts.
- Commands represent requests.
- Controller state changes only while processing Domain Events.
- Services own their internal state.
- Services communicate through Domain Events, Commands and synchronous queries.
- Business logic remains independent of transports and hardware.
- Physical Devices remain simple command executors and event producers.
- Event processing remains deterministic.
